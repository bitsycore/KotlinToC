# ktc2 - Kotlin to C

Source-to-source transpiler: **Kotlin -> C11**, with real Kotlin semantics (the front end is the
Kotlin K2 compiler) on automatic reference counting, no GC.

## What you need
- A JDK to start Gradle. Gradle then fetches JDK 21 (the toolchain), the Kotlin compiler `2.5.0-RC` and the stdlib sources: the first build needs the network and takes a few minutes.
- gcc on the path (mingw on Windows; on macOS `gcc` is Apple clang, which takes the same options): the tests build with it. `KTC2_CC` names another compiler, but the tests' options are gcc's.
- For anything that depends on the `sdl3` module: git, CMake, and a generator CMake can use.
- Python 3 for `tools/*.py`; Git Bash on Windows for `tools/*.sh`.
- The gate is the suite, run locally (Windows with gcc, macOS with Apple clang on ARM64) and by the CI job on every push (`.github/workflows/test.yml`: Linux, macOS, Windows; `gh run list --repo bitsycore/KotlinToC` shows it). All three pass; on Linux the job then runs every program under AddressSanitizer (`tools/asan_all.sh`). On a Windows machine with WSL, Linux is `wsl -e bash -lc "cd /mnt/c/<checkout> && ./gradlew test --rerun"`: it shares `build/` with Windows, so one at a time (`.gitattributes` keeps the shell scripts with Unix line ends for that). There, use `KTC2_TEST_FORKS=4`: eight processes starting at once take more than the 15 GB the WSL machine has, and the machine dies (`Wsl/Service/E_UNEXPECTED`; `wsl --shutdown` brings it back). A test program that asks for a huge block passes on Windows, which never touches it, and takes Linux down: the CI job then shows "The operation was canceled".

## Build / Run / Test
- Build the tool: `./gradlew installDist` -> `build/install/ktc2/bin/ktc2`. Do it again after a change before using the installed tool or `tools/try_cmake.sh`.
- Translate, build, run: `ktc2 <module dir | file.kt | lib.def>... [-o dir] [--build | --cmake | --run [-- args]] [--debug] [-copt x] [-lopt x] [-ea] [--checks=abort] [--warn-heap] [--no-warn-cycles] [--dump-ir]`
- Tests: `./gradlew test --rerun` runs the four categories of the suite, each built as C (gcc, `-O1 -Wall -Werror`, leak check) and run, and compared with the same sources on the JVM: `integration` (every `integration/**/*.kt`, and the programs of several modules under `integration/modules/`), `kotlin` (the files of common tests, `@Test` functions with `kotlin.test` and no `main`, of `tests/kotlin/`, the Kotlin standard library's and Kotlin/Native's runtime's, and of `tests/common/`, ktc2's own: `tests/README.md`; a run fails when a test fails on either), `box` (the box tests under `tests/box/`) and `libraries` (the bundled libraries' own tests under `tests/libraries/`). `KTC2_TEST_CATEGORIES=integration,kotlin` runs only those named; `KTC2_TEST_NO_JVM=kotlin` runs the categories named in C only, a file of tests then deciding by its own assertions. The CI job runs `integration`, and `kotlin` in C only. About eight minutes on a 16-core Windows machine, most of it the large test files of the Kotlin library (`ArraysTest`, `CollectionTest`), three of them the box tests; it was 70 seconds before those (it was about 10 minutes, and 5 on a Mac, with one program after another): the programs are shared between several processes, each of which analyses the library once for all its programs. Without `--rerun` Gradle may answer "up to date" and run nothing.
  - `KTC2_TEST_FILTER=<path part>` runs a subset in under a minute (`objects/`, `stdlib/Regex`, `projects/`); several parts separated by commas run each (`Borrowing,LastUse`). `integration/` alone is every program, about 2 minutes: the place to check a change quickly.
  - Each program and each file of tests is a line as it ends, with the progress of the run (`[412/1034 40%]`), its category (integration, kotlin, box, libraries), green ✔ or red ✘ and its time; under a file of tests where one failed each of its test functions is a line, and under a failure its reason and what it printed; a summary at the end; each program's line has the time of its steps (Kotlin → IR, IR → C, C → exe, run) and the summary their totals. `KTC2_TEST_FUNCTIONS=1` shows the functions of every file, `KTC2_TEST_QUIET=1` prints only the failures and the summary, `NO_COLOR=1` leaves out the colors (`build.gradle.kts`).
  - `KTC2_TEST_FORKS=<n>` says how many processes share the programs (default: half the processors but no more than 8; at most 12; each takes up to 2 GB). `KTC2_TEST_JOBS=<n>` says how many C compilers work on one program at once (default 4). `KTC2_KEEP_LIBRARY=0` has each program compiled with the library from nothing, as a single `ktc2` command does. `KTC2_TEST_FORKS=1 KTC2_TEST_JOBS=1 KTC2_KEEP_LIBRARY=0` is the suite as it was.
  - `KTC2_TEST_UNITY=1` compiles the C of each program as one file (`ktc2_all.c`, which every compilation writes next to the others; the runtime `ktc2_core.c` is compiled beside it) by one compiler, instead of each file by itself. It passes, and takes the same time on a Mac; the default stays one file at a time, which is how a program is built and what finds a C file that lacks an include.
  - A run of the whole suite does not write the dumps (`ir.txt`, `kir/`: 25 MB a program); a run with `KTC2_TEST_FILTER` does, and `KTC2_TEST_DUMP=1` or `=0` says so directly.
  - `build/integration/times.txt` holds, for each program of the last run, the milliseconds of each step (`translate`, `jvmCompile`, `jvmRun`, `cCompile`, `cRun`).
  - `python tools/failures.py` summarizes the failures of the last run.
  - `tools/native.sh [part of a path]`, after a run of the suite, runs the tests that are plain Kotlin with Kotlin/Native too (a compiler under `~/.konan`, or `KTC2_KONAN`) and lists those that print something else there or do not compile there: `build/native/report.txt`. About five minutes. Where the JVM and Kotlin/Native differ, ktc2 is with Kotlin/Native (`PLAN.md`, "Decided by the owner", 2026-11-15; it was the JVM before). The compiler there may be older than the Kotlin ktc2 follows (2.4.21 on the Mac): where they disagree, the sources of Kotlin/Native at the tag of `gradle/libs.versions.toml` decide (github.com/JetBrains/kotlin, `kotlin-native/runtime/src/main` and `libraries/stdlib/native-wasm`). A program that prints what the two do differently gets Kotlin/Native's output as its `.expected`, with a line at its top saying so.
  - `tools/asan_all.sh [part of a name]` does that for every program a run of the suite left (several minutes); the CI job does it on Linux (`.github/workflows/test.yml`: the suite on Linux, macOS and Windows on every push).
  - `tools/asan.sh build/integration/<Name>` (or `build/try`) builds the generated C of one program with AddressSanitizer and without the pool, and runs it. On Windows it uses clang (mingw's gcc has no sanitizer).
  - `tools/msvc_all.sh`, on Windows after a run of the suite and with `cl` on the path (after `vcvars64.bat`), compiles the one C file of every program with MSVC and compares what it prints with gcc's build; `tools/msvc_known.txt` lists what is left out and why. The CI job runs it.
  - `tools/try.sh <group/Name>` builds and runs one program as the tests do, through Gradle, so it always uses the current sources. `tools/try_cmake.sh <group/Name> [cmake args]` builds it through CMake (with no arguments on Windows: MSVC).
  - A test with a `<Name>.expected` is compared with that file instead of the JVM (C interop); `<Name>.def` is its C library; `<Name>.in` its standard input.
  - `tests/libraries/` holds the bundled libraries' own tests (`kotlinx-io`, `kotlinx-collections-immutable`, `atomicfu`, `kotlinx-datetime`, `kotlinx-serialization`, `kotlinx-serialization-json-io`; `commonTest`, and `concurrentTest` for atomicfu), most of the suite's time, run against the bundled module in C and against the library's jars on the JVM (`tests/README.md`). A `.vary` line `/regex/` leaves out whole lines (a duration).
  - `tests/box/` holds box tests of the Kotlin compiler (a `fun box(): String` that returns "OK"), the coroutines' for now, taken by `tools/select_box.py`; `tests/box/pending/` those that do not pass yet (`tests/README.md`).
  - Next to a file of `tests/kotlin/`: `<Name>.with` names other test files whose helpers it uses, `<Name>.skip` the tests not run (`name: why`), `<Name>.vary` the beginnings of the lines that differ on every run, `<Name>.jvm` options of its JVM compilation, `<Name>.cycles` why it may leave objects allocated; `tests/kotlin/support/` holds the helpers of the library's tests (`tests/README.md`).
  - Next to a file of tests: `<Name>.cycles` says (with the reason) that it leaves objects in a cycle, which is then no failure; `<Name>.skip` lists test functions left out, one `name: reason` a line; `<Name>.pending`, for a file of a library's tests, keeps the whole file out until it passes; `<Name>.native`, for a test of Kotlin/Native's own runtime, lets its JVM run fail where the JVM and Native differ; `program.cycles` in the directory of a program of several modules. `<Name>.jvm` holds options of the JVM compiler for that file only.
  - A test with a `<Name>.errors` must be refused by ktc2, with a message containing each line of that file (`integration/errors/`). One with a `<Name>.warnings` must be accepted with a message containing each line of that file.
  - `examples/` are programs for a desktop (the showcase opens an SDL3 window), built and run by hand: not part of the suite.
- `KTC2_CC` names the C compiler (default: the first of gcc, clang, cc on the path); `KTC2_CMAKE_ARGS` adds CMake arguments; `KTC2_LTO=0` builds a release without link-time optimization; `KTC2_TIMING=1` prints where compile time goes; `KTC2_DEBUG_BORROW=1` explains reference-count decisions; `KTC2_DEBUG_CYCLES=1` reports the cycles of the library's own classes too; `KTC2_DEBUG_PASSES=1` prints how many calls were made direct and how many array accesses were proven in range; `KTC2_SKIP=devirtualize,copies,listloops,ranges,handover,brief,walk,owned,slots,rooms,inline` leaves optimizations out; `KTC2_DAEMON=0` runs a command in its own process instead of handing it to the compiler process `ktc2` keeps running (`ktc2 --stop-daemon` ends that one; runs through Gradle never use it).
- Benchmarks: `python tools/bench.py [name] [--compare saved.txt] [--copt -flto]` builds `benchmarks/*.kt` with the installed tool and prints time, allocations, retains, releases and size (`build/bench/results.txt`).
- Against Kotlin/Native and the JVM: `./gradlew compareClasspath` once, then `python tools/compare.py [name] [--targets ktc2,native,jvm] [--runs N]`: compile time, size, peak memory and speed of each (`build/compare/compare.txt`). Kotlin/Native from `KTC2_KONAN`, else `~/.konan` (`./gradlew fetchKotlinNative` puts the version of `gradle/libs.versions.toml` there); `benchmarks/native/ktc2/` is the `ktc2.` package for it.
- The showcase (`examples/showcase`, SDL3, 8 pages): `ktc2 examples/showcase --run`; `-- --auto` goes through every page and reports, `--shot <dir>` keeps a picture of each, `--headless` runs its self-tests. Without a screen: `SDL_VIDEODRIVER=dummy`. On Windows build it with gcc (`KTC2_CC=gcc KTC2_CMAKE_ARGS="-G Ninja -DCMAKE_MAKE_PROGRAM=<ninja>"`): MSVC lacks the POSIX headers kotlinx-io's files use (`PLAN.md`, next steps, item 2).
- In an IDE: the Gradle project has `ide/`, source sets of `stdlib/` (the platform layer), `tests/` and `integration/` with what each needs on its class path (`ide/build.gradle.kts`).

## Architecture (`src/main/kotlin/com/bitsycore/ktc2/`)
- Pipeline: Kotlin K2 compiler (embeddable, pinned in `build.gradle.kts`; run whole by `K2Frontend.kt`, or phase by phase with the library kept by `PhasedCompiler.kt`) with the `Ktc2Extension` IR plugin (`frontend/K2Frontend.kt`) -> `JavaUseCheck` -> `KirImporter` + `BodyBuilder` (`frontend/KirImport.kt`, `BodyLowering.kt`, with `Captures.kt`: IR -> KIR, monomorphizing from `main`) -> `CycleLint` -> `Devirtualize` -> `ListLoops` -> `RangeChecks` -> `ExceptionLowering` -> `EscapeAnalysis` -> `ArcInsert` (with `Effects`, `BorrowedReturns`) -> `CEmitter` (`backend/`).
- KIR, the intermediate form, is `kir/Kir.kt` (`KirCopy.kt` copies a function, `KirDump.kt` writes it as text: a new kind of statement or expression has to be added to both). The C runtime is `src/main/resources/ktc2/ktc2_core.{h,c}`; everything specific to one C compiler is in one block at the top of the header.
- The standard library is the real Kotlin stdlib sources (listed in `stdlib/files.txt`, fetched by Gradle; what Kotlin/Native shares with Wasm, `commonNonJvmMain` and `nativeWasmMain`, comes from the sources jar of `kotlin-stdlib-wasm-js`: number text, Unicode tables and casing, each a level of its own above the platform layer) plus a platform layer, the `Ktc2*.kt` files next to that list (a directory of its own, carried as resources under `ktc2/stdlib`; `ide/` makes it a source set an IDE reads). `hidden.txt` lists the classes of the stdlib jar hidden from the compilation.
- C interop (`interop/`): `.def` files -> generated bindings over `kotlinx.cinterop`; `platform.posix` is generated on demand.
- Modules (`Project.kt`): `module.ktc2.toml` with `name`, `executable`, `main`, `sources`, `dependencies` (a path, a bundled module, or a git URL `url#dir@tag`), `fetch`, `compilerOpts`, `linkerOpts`, `cmake`, `weak` and `acyclic` (properties of its sources that are as if `@Weak` or `@Acyclic`: for a library taken as it is; an inner object's reference to its outer one is `Outer.Inner.this$0`), `optIn` (what its sources are compiled opted in to), and for a bundled module `files` (or a `files.txt`; a line `windows: path` or `linux, macos: path` is a file of those systems only, as a library's source sets are). Bundled modules are under `resources/ktc2/modules/` (`sdl3`, which fetches SDL3 and builds it with CMake; `kotlinx-io`, `kotlinx-collections-immutable`, `atomicfu`, `kotlinx-serialization` and `kotlinx-datetime`, the sources of those libraries that Gradle fetches (`kLibraryModules` in `build.gradle.kts`), as it does the standard library's). A module's sources under `commonMain` or `concurrentMain` are common code; those of a Kotlin/Native source set (`nativeMain`...) are compiled with `import kotlin.native.*` added, as Kotlin/Native imports it (DESIGN.md, section on modules). Each compilation writes a `CMakeLists.txt` next to the C.

## Rules of the design
- Plain Kotlin behaves as on Kotlin/Native (the owner, 2026-11-15): ktc2 is a native target, and what Kotlin/Native gives native code ktc2 gives too, so that libraries' `nativeMain` compiles as it is. Where the JVM and Kotlin/Native agree (nearly always) the tests enforce it against the JVM, which is fast and everywhere; where they differ ktc2 does as Kotlin/Native, and the test says so (an `.expected` file, or `samePlatform` in `IntegrationTest.kt`, which takes the JVM's `java.lang.IllegalStateException` for Kotlin/Native's `kotlin.IllegalStateException`). A difference from both is a bug. `DESIGN.md`, section 1.
- Memory is the one difference allowed, never results: a cycle Kotlin/Native's collector would free is answered with `weak`/`acyclic` in a module file where the library's design makes it harmless, a bounded cache, or a known leak written in `PLAN.md`; never a weak reference that changes what a program computes.
- ktc2-only features live in the `ktc2.` package (`@Struct`, `@SimpleEnum` with `@EnumValue` and `enumOf`, `@Value`, `@Size`, `arena`, `ValueArray`, `@Weak`, `WeakRef`, `@Acyclic`, `createCleaner`, and `ktc2.concurrent`: `Thread`, `thread`, `synchronized`, `sleep`). Each changes storage and cost, never behavior. The exception is when an object ends: a cleaner (`createCleaner`: Kotlin/Native's API, over `java.lang.ref.Cleaner` on the JVM) runs in C at the last release, and on the JVM whenever the collector gets to it. A test of that has an `.expected` file. There is no `Deinit` any more: the cleaner is the one way, the same on every target.
- As in Kotlin/Native a program has no JDK: nothing of `java.*` (reported by `JavaUseCheck`). Do not add anything under `java.*` for programs to use; files and similar are to come from kotlinx libraries (kotlinx.io or okio) through ktc2 compatibility layers. The one platform file in package `java.lang`, `Ktc2JavaLang.kt`, is not an exception to this: it only declares the exception classes the runtime throws under their JVM names (`ArrayIndexOutOfBoundsException`...), which Kotlin code can catch by their Kotlin supertypes.
- Memory: objects are references, counted; `EscapeAnalysis` moves them to the frame, `ArcInsert` leaves out the counting nobody can observe. Two objects that hold each other (an object and its `inner` object or self-calling lambda) are freed by the runtime when nothing else holds them (`KClass.pairCycles`, not with threads); other cycles are reported at compile time (`@Weak` on a property or an `inner` class, `WeakRef`, `@Acyclic`); there is no cycle collector.
- Exceptions are a pending value tested after each call that can throw; no `setjmp`.
- Coroutines are `suspend` functions turned into state machines, as on Kotlin/Native (`DESIGN.md`, "Coroutines"): `sequence { }`, `iterator { }`, `DeepRecursiveFunction`, `startCoroutine`, `suspendCoroutine`. The library's coroutine classes are in the platform layer (`Ktc2CoroutineSupport.kt`, `Ktc2Coroutines.kt`, `Ktc2CoroutineIntrinsics.kt`).
- Not supported: reflection beyond a class as a value (`x::class` compared and named) and `typeOf<T>()` (a `KType`: class, arguments, nullability, as on Kotlin/Native), and what only the JDK has (`String.format`, `toSortedMap`...).

## How to
- **Fix a difference from Kotlin**: write the program under `integration/<group>/`, see it fail against the JVM (or against Kotlin/Native's output, where the two differ), fix, run the tests that cover it, commit.
- **Take more of Kotlin/Native's own library code**: what Native shares with Wasm (`commonNonJvmMain`, `nativeWasmMain`) is unpacked into `build/stdlib-src` from the sources jar of `kotlin-stdlib-wasm-js`; list a file in `stdlib/files.txt` and write in the platform layer the `actual`s it leaves (Native's runtime has them, `kotlin-native/runtime/src/main/kotlin`). Delete `build/stdlib-src` if a change to what Gradle unpacks does not show.
- **Add a test**: one `.kt` file with its own `fun main()` (a package is allowed), in the group it fits (`basic`, `objects`, `generics`, `stdlib`, `values` for the `ktc2.` package, `interop` for C). Give it a file name no other test has: the name is its build directory and its key in the counts. What it prints must be the same on every run: no times, no addresses or default `toString()` of objects, no order that depends on threads. For C interop, where the JVM cannot run it, write `<Name>.expected` by hand or from the C output after checking each line. A program that must fail to compile goes to `integration/errors/` with a `<Name>.errors` file.
- **Add a common test**: a file under `tests/common/` written as Kotlin Multiplatform's common tests are (classes with `@Test` functions, `kotlin.test` assertions, no `main`): see `tests/README.md`. It runs in C and on the JVM in the suite (`KTC2_TEST_FILTER=tests/common/`) and on Kotlin/Native with `tools/native.sh tests/common/`. Prefer it to a program whose output is compared when the test is about what must hold everywhere; the programs under `integration/` stay, for what is seen by running a whole program.
- **Look for differences from Kotlin**: write a program of what ordinary code does with one part of the language or the library, as a test; run it with `KTC2_TEST_FILTER`; `tools/jvmdiff.sh <Name>` shows the lines where the C output and the JVM's differ ("not supported yet" comes first, from `tools/try.sh`). Five such programs found some twenty differences (`PLAN.md`, "Looking for differences on purpose").
- **Find out why a test fails**: `python tools/failures.py` for the first lines; then `tools/try.sh <group/Name>`. Its directory `build/try/` (or `build/integration/<Name>/` after a run of the suite; the dumps are there after a run with `KTC2_TEST_FILTER`) has `c/` (the generated C), `kir/` (KIR as text after the importer and after each pass: `diff kir/3-escapeanalysis.txt kir/4-arcinsert.txt` shows what `ArcInsert` did; the program's own functions, or with `KTC2_DUMP_KIR=<part of a C name>` or `=all` the library's), `ir.txt` and `ir.kt.txt` (the Kotlin IR the importer received), `jvm/` (the classes it was compared with), `stdlib/` and `interop/` (the library and binding sources that were compiled in; in the suite and through the compiler process the library sources are not copied there but to `<temporary directory>/ktc2/library-<process id>/stdlib/`), `ktc2_build.txt` and `program.exe`. "not supported yet: ..." comes from the importer with a file and a line. `ktc2: leak: N object(s) of type X` at exit means a count was not given back. A crash or nonsense output after a change to counting is a use of freed memory: test builds fill freed objects with `0xDD`. A program has 300 seconds and a C compiler 900 (`kTimeoutSeconds`, `kCompileTimeoutSeconds` in `IntegrationTest.kt`). To step through the transpiler, run `IntegrationTest` under a debugger with `KTC2_TEST_FILTER` set (by itself that class takes every program; under Gradle it is one of the parts, `IntegrationTest01` to `11` being the others): the passes run inside the Kotlin compiler, in the same process.
- **Add a library function**: if the Kotlin stdlib has it in common code, add its file to `stdlib/files.txt`; if it is an `expect`, write the `actual` in the matching `Ktc2*.kt`. If the program then fails to compile with an ambiguous call or a JVM type inside library code, the jar's JVM version is competing: hide its class in `hidden.txt`. A function that needs the runtime is an `external fun` in `ktc2.internal` (`Ktc2Internal.kt`), implemented as `ktc2_<name>` in `ktc2_core.c` and declared in `ktc2_core.h`.
- **Add something to the `ktc2.` package**: it is declared twice, with the same signatures: for the JVM in `src/main/kotlin/ktc2/`, for C in the platform layer (`stdlib/Ktc2Lifetime.kt`, `Ktc2Concurrent.kt`). Annotations are recognized by name in the importer (`frontend/KirImport.kt`).
- **Regenerate a generated source** (from the repository root; change the script, not the file): `python tools/gen_arrays.py` (`Ktc2Arrays.kt`), `python tools/gen_math.py` (`Ktc2Math.kt`), and `python tools/gen_comparisons.py` (`Ktc2Comparisons.kt`).
- **Change reference counting or escape analysis**: copy `build/integration/arc-stats.txt` first and compare after with `tools/arc_compare.py` (after a filtered run the file holds only the subset). A wrong answer is a use of freed memory: run the whole suite, and add the case to `integration/objects/Borrowing.kt`, `LastUse.kt` or `ThreadBorrowing.kt` (to `integration/values/CleanerLifetimes.kt` when it is about code that runs under a release). Test builds report a retain or release of a freed object; for what that misses, build the C of `build/integration/<Name>/c` with `-fsanitize=address -g -DKTC2_NO_POOL` (the command is the one of `tools/try.sh` plus those options; without `KTC2_NO_POOL` small objects come from the runtime's own lists, which AddressSanitizer does not watch) and run it.
- **Find which optimization breaks a program**: `KTC2_SKIP=<name>` with the installed tool, one name at a time (each new value starts the compiler process again: a first compilation of 13 s each time). `Devirtualize` wrongly sure of a class shows as a crash or a wrong method inside library code (see "Where a small mistake costs most" in `DESIGN.md`).
- **Measure a change to speed**: `python tools/bench.py --save before.txt` first, then `--compare before.txt`; `KTC2_TOOL` names an installed tool of another state of the sources.
- **Try another compiler**: `tools/try_cmake.sh <group/Name>` for MSVC; `KTC2_CC=clang tools/try.sh <group/Name>` for clang.

## Things that cost time before
- After a run of Gradle on the other system of a checkout shared between Windows and WSL, the Kotlin compile of ktc2 itself fails with "Expected absolute path but found relative path": delete `build/kotlin` and `build/classes/kotlin`.
- The tests of the Kotlin standard library (`tests/kotlin/`) have to be of the tag of the library ktc2 compiles (`v2.5.0-RC`): a file of another version fails on the JVM as well, which looks like a difference and is not one.
- Several Kotlin compilers at once slow each other down, through memory and not through the processors (8 at once: each takes twice as long; the machine is half idle meanwhile). The suite gains about 3.5 times from its processes, not 8 or 12, and a first compilation in each costs half a minute then. Do not expect more from more processes.
- A change that makes a library function unable to throw changes the shape of its callers (no test after the call), and a pass that only knew the old shape then quietly stops applying: the counts of `tools/bench.py --compare` show it at once (retains of Collections went from 8.7 M to 38.7 M once). Compare the counts, not only the times, after any change to the library or to `ExceptionLowering`.
- A function and the forms made of it (`name__into`, `__b`, `__m`, `__o`) share their statements: a pass that rewrites a statement in place rewrites it in each of them. What it adds to one body (a declaration) has to be added to the others (`declareRooms` in `EscapeAnalysis` is the example).
- A compilation in a process that keeps the library (`PhasedCompiler.kt`: the suite, the compiler process) is not the same code path as a single `ktc2` command (`K2JVMCompiler.exec`): the program is a part of its own on top of the library's. If something differs between `./gradlew test` and `KTC2_DAEMON=0 ktc2 ...`, or only shows after several programs in one process, try `KTC2_KEEP_LIBRARY=0`. That file calls the compiler's internals step by step and has to be gone over when the Kotlin version changes.
- The installed `ktc2` hands its command to a process that stays (`Daemon.kt`). It is replaced after `./gradlew installDist` and when a `KTC2_*` variable or `PATH` changes, so it never runs old code; if something still looks stale, `ktc2 --stop-daemon`, and `~/.ktc2/daemon.log` holds what that process printed for itself.
- Shell heredocs mangle backslashes, `$` and tabs in Kotlin and C text. For an edit with any of those, write a small Python script to a file (with exact-match replacements that assert they matched once), run it, delete it.
- Inside a platform file in package `java.lang`, plain `String`, `Long`, `Boolean` and the exception names resolve to the Java classes: write `kotlin.String`.
- A new platform function that has the same JVM signature as another needs `@JvmName`.
- The JVM the tests compare with runs with an English locale on purpose: number formatting follows the locale otherwise.
- Example `build/` directories hold CMake caches with absolute paths: delete them after moving anything.
- CMake's default generator on Windows is Visual Studio, that is MSVC. For gcc or clang pass a generator in `KTC2_CMAKE_ARGS` (`-G Ninja -DCMAKE_MAKE_PROGRAM=<ninja>`) and set `KTC2_CC`. The first build of a program that uses `sdl3` fetches and compiles SDL3: about a minute.
- A compile error inside library sources that makes no sense: see "Where a small mistake costs most" in `DESIGN.md` (the cached jar, `hidden.txt`).
- A use of freed memory can pass on one system and crash on another: the double release found on macOS had always passed on Windows. Trust AddressSanitizer over a green run.
- Apple's SDK declares the C library in private headers (`_stdio.h` behind `stdio.h`): `Bindings.kt` adds them to the headers a `.def` asks for.
- Do not run the benchmarks or the installed tool while the suite runs: the machine is busy enough to make times meaningless.
- The last digit of `exp`, `ln`, `pow` differs between C libraries and from the JVM: a test must not print it.

## Conventions
These are what the code uses; follow the code where another instruction differs.
- Kotlin: standard Kotlin conventions, tabs, KDoc on classes and functions; section markers `// ====` + `// MARK: Name` between major groups; concise comments only when non-obvious, saying what the code is for and not how it changed.
- Names in the transpiler's source and in the `ktc2.` package: locals `v...`, parameters `in...`, private members `m...`, constants `k...`. Parameters have no prefix where the name is the API: overrides of library members, platform functions that stand for library ones, and `ktc2.concurrent`.
- Generated C and the runtime: K&R style, doc comments with `/** */`.
- No em dashes anywhere: plain punctuation.
- Commits: one logical change each, only when the suite is green.
